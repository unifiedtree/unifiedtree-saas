# Phase 0 audit: Admin dashboard

Area: the admin dashboard at `/dashboard` (prototype `PgDashboard.dc.html`, default layout = outlined-pill section header + quick-action tile row, with `UtLive`, `UtQuick`, `UtStat`; older variant `PgDashboardV1.dc.html`).
Repo: `C:\REACT\unifiedtree-saas` at `e32a4dc6`. Read-only audit. Nothing in the repo was changed.

**Live check:** not possible during this audit. The API (`127.0.0.1:8080`) and the recovery database (`127.0.0.1:55432`) refused connections; the Postgres on 5432 is a different instance with other credentials. Everything below is from the code (frontend, backend, Flyway migrations) and the e2e scripts.

Legend used in the tables: **exists** = real data or a real API is already there; **partial** = most of it is there, the missing piece is named; **missing** = no data source or API today.

---

## 1. Summary

- The current dashboard (`AdminDashboardContainer` + generated `design/dc/AdminDashboard.view.tsx`) already reads real data for almost everything the new design shows, follows `?date=` for past days, hides sections the viewer can't read, and has loading / empty / error states per card.
- The new design **reorganises** the page into six sections driven by top-bar pills (Overview, Attendance, Upcoming, People, Hiring & projects, Payroll & activity) and **adds** interactive pieces: an inbox with inline approve / reject / remind, a people list for today's attendance, quick actions sorted by use with Customise, per-project owner / due / health, a hiring funnel with conversion, and a paid-vs-in-review payroll chart.
- What needs **backend work**: Customise + usage for quick actions (new table), Remind (new endpoint, no table), approval Undo (shared with the Approvals area), headcount sparkline and "joined this month" for today, performers summary, onboarding sub-line fields, hiring "this quarter" + funnel, project owner / due date / health (new columns on a JDBC-only table). Everything else is frontend on existing endpoints.
- The design **drops** things the client already has (Company summary tiles incl. Compliance completion, Operational insights, the donut with Early departures, the notices Edit / Archive / pager, the seats tile when seats are healthy). The prompt says nothing may be removed without approval, so each is listed in §14 with a proposal.
- About 20 live e2e scripts assert today's dashboard markup (§16).

## 13. Quick actions "Customise": end-to-end spec (G1)

**Catalogue** (keys from `hrms-dash.js` `QUICK`; gate = the target page's `PAGE_REGISTRY` rule, so a tile never dead-ends):

| Key | Label | Opens | Gate | Hint (real data) | Badge |
|---|---|---|---|---|---|
| `leave` | Approve leave | `/hrms/leave?tab=approvals` | `hrms.leave.approve.l1` | "N requests waiting" / "Nothing waiting" | pending leave |
| `add` | Add employee | `/hrms/employees?add=1` | `hrms.employee.write` (+ `hrms.employee.read` for the page) | "Start onboarding"; "Add your first hire" at 0; disabled with reason when seats are full | — |
| `pay` | Run payroll | `/hrms/payroll/runs` (current month's run when there is one) | module `payroll` + `payroll.runs.read` | "{Month} is in review / locked / paid", "No run for {Month} yet" | — |
| `fix` | Regularise | `/hrms/attendance?tab=corrections` | `attendance.regularization.approve` | "N requests waiting" | pending corrections |
| `note` | Announce | notice form | `org.company.write`, today only | "Post to everyone" | — |
| `rep` | Reports | `/hrms/reports` (`?asOf=` on a past date) | any `hrms.report.*` | "Headcount, attrition and more" | — |
| `att` | Attendance | `/hrms/attendance?tab=team&date=` | `attendance.team.read` | "{in} of {scheduled} in" | — |
| `shift` | Change shifts | `/hrms/shifts?tab=roster` | `attendance.workforce.admin` + `attendance.team.read` (as today) | — | — |
| `off` | Add time-off | `/hrms/leave?tab=apply` | `leave.request.self` and **not** an admin role (same rule as the Leave page) | — | — |
| `org` | Org setup | `/hrms/organization` | `hrms.department.write | hrms.branch.write | hrms.designation.write` | — | — |

**Behaviour:** permitted tiles only. With picks: the picked ones (still permitted), otherwise all permitted; sorted by uses this month (desc), ties by default rank; first 6 shown. Customise lists every permitted action with a tick and "N×", allows at most 6 ("Pick up to 6 · remove one first"), shows "3 of 6 picked · they still sort by use", has Reset to automatic, Save and Cancel; saving shows a real success / error toast. A tile click records one use (fire and forget).

**Storage** (new migration, JDBC only, RLS by tenant, grants like `V135`):
```sql
CREATE TABLE hrms.user_dashboard_prefs (
  tenant_id     uuid NOT NULL,
  user_id       uuid NOT NULL,               -- JWT sub (auth.user_credentials.id)
  quick_actions text[],                      -- picked keys in order; NULL = automatic
  quick_uses    jsonb NOT NULL DEFAULT '{}', -- {"month":"2026-09","counts":{"leave":41,...}}
  updated_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, user_id));
```
**Endpoints** (`@PreAuthorize("isAuthenticated()")`, identity from the session only, like `/v1/me/notification-preferences`):
- `GET /v1/me/dashboard/quick-actions` → `{ available, picked: string[]|null, month, uses: {key: n} }`; `available:false` when the table doesn't exist yet (UI then hides Customise and uses the default rank; the "Most used first" line only shows when usage is available).
- `PUT /v1/me/dashboard/quick-actions` `{ picked: string[]|null }` → validates ≤ 6, unique, known keys; row-locked read-modify-write.
- `POST /v1/me/dashboard/quick-actions/{key}/use` → +1 for the current IST month (counts reset when the month changes); 204.
No new permission needed. Tests: validation, month rollover, missing-table fallback, other-user isolation; one live e2e.
