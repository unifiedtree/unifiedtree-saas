# Deploy checklist: database, backend, web app (26 Sep 2026)

**Who this is for:** the teammate deploying `main` to production.
**What it is:** the one checklist to follow, top to bottom. It covers the database, the backend and the web app, then a smoke test for each role.
`DEPLOY_2026-09-25.md` and `DEPLOY_2026-09-26_WAVE3.md` are background now. Everything you need from them is repeated here.

Do the steps in order. **The database goes first.** The new backend won't start on an old database, and Cloud Run then quietly keeps the old backend running. The new web app talking to an old database or an old backend is the likely cause of the 500 errors seen on 26 Sep. Step 7 shows how to confirm it for each error.

---

## 0. Before you start

You need:
- GCP project `unifiedtree-prod`, region `asia-south1`:
  - Cloud SQL instance `ut-postgres`, database `railway`.
  - Cloud Run service `unifiedtree-saas`.
- A **superuser** login for the database (see step 3.1 for why).
- The GitHub repo (Actions tab) and the Vercel project for `apps/platform`.
- A local checkout of `main`: `git checkout main && git pull origin main`.

Facts that shape this checklist:
- **Production never migrates itself.** Cloud Run starts the app with `SPRING_FLYWAY_ENABLED=false` (`deployments/gcp/provision.sh`). You apply migrations by hand.
- **The backend deploys itself** when a push to `main` changes `backend/**` (`.github/workflows/gcp-backend-deploy.yml`).
- Hibernate runs with `ddl-auto: validate`. If a column it maps is missing, the new revision fails its startup check and Cloud Run keeps the old one serving. Nothing tells you.
- **The app refuses to start** unless the OWNER role holds every permission (`OwnerPermissionInvariantCheck`). Every migration below grants its new permissions to OWNER in the same file.

## 3. Find what production already has (10 min)

### 3.1 Connect as a superuser

The Cloud SQL Auth Proxy is the easiest way:
```bash
cloud-sql-proxy unifiedtree-prod:asia-south1:ut-postgres --port 6543 &
psql "host=127.0.0.1 port=6543 dbname=railway user=<superuser>"
```

Check the login:
```sql
SELECT rolname, rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user;
```
**`rolsuper` or `rolbypassrls` must be `t`.**
- Why: most tables have row-level security, and several migrations fix data in them (V143_11, V143_22, V143_23, V143_26, V143_31, V143_32, V143_33 and others).
- A login that doesn't bypass row-level security sees no rows there. Those steps then change nothing, and no error tells you.
- If both are `f`, stop and get a login that has one of them before you apply anything.

### 3.2 Look at the Flyway history

```sql
SELECT to_regclass('public.flyway_schema_history_canonical');   -- null: there is no history table

SELECT installed_rank, version, description, success, installed_on
  FROM public.flyway_schema_history_canonical
 WHERE version LIKE '14%'
 ORDER BY installed_rank;
```
Files applied with plain `psql` are **not** recorded there. So treat the history as a hint only. The status query below is the real answer.

How to read it:
- `00000000-0000-0000-0000-000000000010` is the built-in OWNER role (the same id the startup check uses).
- Most checks look at the **last** thing the file does, so `t` means the whole file ran.
- V143_12, V143_30, V143_31 and V143_32 only fix data. Their check shows the end state, so it can read `t` before the file ran if there was nothing to fix. Each is safe to run again, so run them when in doubt.
- V143_1 and V143_4 take permissions away, so their check also reads `t` if managers never had them.
- Checked on 26 Sep against a local database that has every migration applied: all 38 rows read `t`.

**Write down every version that reads `f`.** Those are the files for step 4.

> The status query starts at V140. If the history stops before V140, or V140 and V141 both read `f`, production may be older than V140. Then stop: apply the missing earlier files first, in version order (same folder). `V142`'s header says a production rehearsal on 24 Sep had V124–V141 applied to a copy of prod.

## 4. Apply the missing migrations (15–30 min)

Files: `backend/app/hrms-app/src/main/resources/db/canonical/`.

**Order matters: Flyway version order.** It's the order of the table below.
- `V143` comes before `V143_1`.
- `V143_17` comes before `V143_17_1`, which comes before `V143_18`.
- There is no `V143_16`, no `V143_29` and no `V143_35` → `V143_39`. That's expected.

Every file is written to be re-runnable (`IF NOT EXISTS`, `ON CONFLICT DO NOTHING`), **except V141**: its row-level-security policy has no guard, so a second run stops with `policy "offer_email_attempts_tenant" … already exists`. If V141's check (step 4.2) already reads `t`, leave it out of the list below. (The app role's grant on V141's table comes from V142, so re-run V142, not V141, if that grant is missing.) If any other file stops halfway, fix the cause and run it again.

**V143_32 check** (expected `t`: no undecided overtime left to recompute):
```sql
SELECT NOT EXISTS (
  SELECT 1 FROM attendance.records r
    JOIN LATERAL (SELECT sp.start_time, sp.end_time, sp.working_hours_per_day
                    FROM attendance.employee_shift_assignments esa
                    JOIN attendance.shift_policies sp ON sp.id = esa.shift_policy_id
                   WHERE esa.employee_id = r.employee_id AND esa.effective_from <= r.attendance_date
                     AND (esa.effective_to IS NULL OR esa.effective_to >= r.attendance_date) AND sp.is_active
                   ORDER BY esa.effective_from DESC LIMIT 1) sp ON TRUE
   WHERE r.work_hours IS NOT NULL AND sp.start_time IS NOT NULL AND sp.end_time IS NOT NULL
     AND NOT EXISTS (SELECT 1 FROM attendance.overtime_decisions od WHERE od.record_id = r.id)
     AND r.overtime_minutes IS DISTINCT FROM GREATEST(0, ROUND((r.work_hours - GREATEST(
           EXTRACT(EPOCH FROM (sp.end_time - sp.start_time)) / 3600.0 + CASE WHEN sp.end_time > sp.start_time THEN 0 ELSE 24 END,
           COALESCE(sp.working_hours_per_day, 0))) * 60))::int);
```
It reads `t` right after the file runs. It can drift to `f` later if someone changes a shift's times after those days; that's harmless.

## 5. Deploy the backend (10–15 min)

### 5.1 What is serving now

This push **does** change `backend/**` (the company-restore change: `WorkforceController`, `CompanyService`, `WorkforceCompanyRepository`), so **it starts a backend deploy by itself.** That change needs no migration. But if production's database is still missing migrations from step 4, the new revision fails its startup check and Cloud Run keeps the old revision serving. After step 4, run the backend workflow again (step 5.2) so the latest code starts. Best: finish step 4 first.

Look at the service:
```bash
gcloud run services describe unifiedtree-saas --region asia-south1 --project unifiedtree-prod \
  --format='yaml(status.latestCreatedRevisionName,status.latestReadyRevisionName,status.traffic)'
```
- If `latestCreatedRevisionName` differs from `latestReadyRevisionName`, **the newest deploy failed to start.** Traffic is still on the older revision. That is the silent failure described at the top. The usual cause is the missing migrations from step 4.

### 5.2 Deploy

After step 4 is done:
1. GitHub → Actions → **Deploy backend to Cloud Run** → **Run workflow** on `main`.
   - It builds, runs the backend tests, builds the image, deploys a revision and checks `/api/actuator/health`.
   - If Actions isn't set up (repo variables `GCP_*` missing), deploy by hand (`RUNBOOK.md` §1b): `cd deployments/gcp && ./provision.sh deploy`.
2. Run the command from 5.1 again. `latestCreatedRevisionName` and `latestReadyRevisionName` must now be the same, and `status.traffic` must send 100% to it.
3. Check that the serving revision has every backend change on `main`:
   ```bash
   gcloud run revisions describe <REVISION> --region asia-south1 --project unifiedtree-prod \
     --format='value(spec.containers[0].image)'
   # …/hrms-backend:<first 12 characters of a commit>
   git fetch origin
   git log --oneline <those 12 characters>..origin/main -- backend/
   ```
   **No output** means the revision has every backend change on `main`. Any output means it's older: run the workflow again. (The workflow tags each image with the first 12 characters of the commit it built. A tag that isn't a commit means a manual deploy; redeploy through the workflow so you know what's running.)
4. `curl -s https://<service-url>/api/actuator/health` → `{"status":"UP"}`.

### 5.3 Startup log lines

Open the new revision's logs (Cloud Run → `unifiedtree-saas` → Revisions → the revision → Logs), or:
```bash
gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="unifiedtree-saas" AND resource.labels.revision_name="<REVISION>"' \
  --project unifiedtree-prod --freshness=1h --limit=500 --format='value(textPayload)' \
  | grep -E 'Started HrmsApplication|OwnerPermissionInvariantCheck|Application run failed|Schema-validation'
```
These must appear:
- `Started HrmsApplication in … seconds`
- `OwnerPermissionInvariantCheck: PASS — OWNER role has every non-platform permission in the rbac.permissions catalog.`

You may also see `KPI at-risk sweep: … marked at risk`.

If you see `Application run failed`, read the lines above it:
- `Schema-validation: missing column [...] in table [...]` or `missing table`: a migration is missing. Find the table name in the step 4 table, apply that file, and deploy again.
  - The files the new backend can't start without: **V140, V143_7, V143_11, V143_13, V143_22, V143_23, V143_24, V143_25, V143_26**.
- `OwnerPermissionInvariantCheck: FAIL … missing N non-platform permissions: [...]`: a migration stopped between adding a permission and granting it. Run that migration again.

**Rollback:** point traffic back to the previous revision (`RUNBOOK.md` §2, about 30 s). The migrations add tables and columns (new required columns have defaults), so the previous revision can run on the new schema. Don't restore the database unless data is actually wrong.

## 7. If you see 500 errors

1. In the browser, open DevTools → **Network**, tick **Preserve log**, and reload the page.
2. Click the red request. Note its path (for example `/api/v1/attendance/policy`), the time and the response body.
   - A 500 usually says `"INTERNAL_ERROR"` / "An unexpected error occurred".
   - A **404** "The requested resource was not found" on a new feature usually means the **old backend** is still serving: go back to step 5.1. Example: on Companies & Branches, **Restore** answers 404, or the Inactive filter never lists archived companies.
3. In Cloud Run logs, look at that time for `Unhandled exception` (unexpected 500s log it with the full error):
   ```bash
   gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="unifiedtree-saas" AND textPayload:"Unhandled exception"' \
     --project unifiedtree-prod --freshness=2h --limit=20 --format='value(timestamp,textPayload)'
   ```
   Then read the lines just after it. The database error names what's missing: `relation "attendance.timing_policies" does not exist` or `column … does not exist`.
4. Find that table or column in the step 4 table ("What it does"). That's the migration to apply. Apply it (step 4.1) and check it (step 4.2), then reload the page. If it still fails, run the backend workflow again (step 5.2) so the backend starts fresh. A new permission shows up after people sign in again.
5. `permission denied for table …` means the app role lacks a grant: run that table's migration again as the table owner (for V141's table, re-run V142).
6. Anything else: send the path, the response body and the log lines to the team.
