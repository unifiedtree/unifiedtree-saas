# Deploy runbook: database + backend + frontend (25 Sep 2026)

**Who this is for:** the teammate deploying the HRMS tonight.
**What it ships:** everything on `main` up to and including the commit that added this file: the full HRMS redesign (frontend) plus the backend fixes and **13 database migrations (V140 → V143_9)**.

Do the steps in order. Don't skip step 2 or step 3: the new backend will not work on the old database.

---

## 0. Before you start

You need:
- Access to GCP project `unifiedtree-prod`, region `asia-south1`.
  - Cloud SQL instance `ut-postgres`, database `railway`.
  - Cloud Run service `unifiedtree-saas`.
- The **migrator** database credentials. That's the role that owns the tables and can `ALTER` them; the app's own `ut_app` role can't run migrations.
- Access to the GitHub repo (Actions tab) and the Vercel project for `apps/platform`.
- A local checkout of `main`: `git pull origin main`.

Facts that shape this runbook:
- **Production never migrates itself.** Cloud Run starts the app with `SPRING_FLYWAY_ENABLED=false` (`deployments/gcp/provision.sh`), so migrations are applied by hand (`docs/production/RUNBOOK.md` §5).
- **The backend deploys itself** when a push to `main` touches `backend/**` (`.github/workflows/gcp-backend-deploy.yml`). It may already have tried to deploy today's commits.
  - Hibernate runs with `ddl-auto: validate`. If the tables it expects are missing, the new revision fails its startup probe and Cloud Run keeps the old one running, so the failure is silent.
  - That's why the database goes first.
- **The app refuses to start** unless the OWNER role holds every permission (`OwnerPermissionInvariantCheck`). The migrations below already take care of that.

## 1. Back up the database (5 min)

```bash
gcloud sql backups create --instance=ut-postgres --project=unifiedtree-prod \
  --description="before V140-V143_9 deploy 2026-09-25"
gcloud sql backups list --instance=ut-postgres --project=unifiedtree-prod --limit=3
```
Wait for status `SUCCESSFUL`. Point-in-time recovery also works as a fallback (RUNBOOK §3).

## 2. Find where production's schema is (5 min)

Connect as the migrator. The Cloud SQL Auth Proxy is the easiest way:

```bash
cloud-sql-proxy unifiedtree-prod:asia-south1:ut-postgres --port 6543 &
psql "host=127.0.0.1 port=6543 dbname=railway user=<migrator>"
```

```sql
-- If this table exists, it lists what has been applied:
SELECT version, description, success FROM public.flyway_schema_history_canonical
 ORDER BY installed_rank DESC LIMIT 15;
```

If the table isn't there, or it stops before V140, run the checks in the "Probe" column of the table in step 3. Each one tells you whether that migration is already in. **Apply every migration that isn't there, in order.**

> If production turns out to be *older than V140*, stop and apply the missing earlier migrations first, again in version order. They're in the same folder. `V142`'s header says a production rehearsal on 24 Sep had V124–V141 applied to a copy of prod, which is a hint where prod may be.

## 3. Apply the migrations (15–20 min)

Files: `backend/app/hrms-app/src/main/resources/db/canonical/`.

Every file below is written to be re-runnable (`IF NOT EXISTS` / `ON CONFLICT DO NOTHING`). **Order matters: version order, V140 first, V143_9 last.**

**Option A (recommended): Flyway CLI**, which also records history:
```bash
flyway -url=jdbc:postgresql://127.0.0.1:6543/railway -user=<migrator> -password=<...> \
  -locations=filesystem:backend/app/hrms-app/src/main/resources/db/canonical \
  -table=flyway_schema_history_canonical -schemas=public -outOfOrder=true \
  -baselineOnMigrate=true -baselineVersion=0 info      # look first
# then the same command with `migrate` instead of `info`
```

**Option B: plain psql, one file at a time**, when prod has no Flyway history table:
```bash
for f in V140__candidate_employee_conversion.sql V141__offer_email_attempts.sql \
         V142__app_role_grants_and_shift_change_requests.sql V143__shift_change_request_effective_dates.sql \
         V143_1__managers_do_not_read_offers.sql V143_2__single_lookup_login_tenant.sql \
         V143_3__auth_rows_cleanup.sql V143_4__manager_perm_lockdown.sql V143_5__attendance_admin_perm.sql \
         V143_6__approval_delegations.sql V143_7__document_types_and_verification.sql \
         V143_8__onboarding_task_delete_keeps_runs.sql V143_9__performance_admin_and_team_kpi_progress.sql; do
  echo "== $f"; psql "host=127.0.0.1 port=6543 dbname=railway user=<migrator>" -v ON_ERROR_STOP=1 \
    -f backend/app/hrms-app/src/main/resources/db/canonical/$f || break
done
```

| Migration | What it does | If it's missing when the new backend runs | Probe (should return a row / `t`) |
|---|---|---|---|
| V140 | Candidate → employee link (`hiring_mgmt.candidates.converted_employee_id`, `converted_at`) | Hiring "Convert to employee" fails; the app may not start (validate) | `SELECT 1 FROM information_schema.columns WHERE table_schema='hiring_mgmt' AND table_name='candidates' AND column_name='converted_employee_id';` |
| V141 | Offer email attempt ledger (`hiring_mgmt.offer_email_attempts`) | Sending an offer email errors | `SELECT to_regclass('hiring_mgmt.offer_email_attempts');` |
| V142 | Grants for the app role on every table; `attendance.shift_change_requests` table | Shift-change requests fail; permission errors on tables | `SELECT to_regclass('attendance.shift_change_requests');` |
| V143 | Shift-change effective dates (`requested_effective_date`, `applied_effective_date`) | Shift-change requests fail | `SELECT 1 FROM information_schema.columns WHERE table_name='shift_change_requests' AND column_name='requested_effective_date';` |
| V143_1 | Department managers stop reading job offers (removes a permission) | Managers can still see offer salaries (security) | `SELECT count(*)=0 FROM rbac.role_permissions rp JOIN rbac.roles r ON r.id=rp.role_id WHERE r.code='DEPT_MANAGER' AND rp.permission_code='hrms.hiring.offer.read';` |
| **V143_2** | **Sign-in lookup functions** (`auth.login_tenant_for_email`, `auth.refresh_token_tenant`, `auth.phone_login_match`) + indexes | **Sign-in and session refresh fail: nobody can log in** | `SELECT to_regprocedure('auth.login_tenant_for_email(text)');` |
| V143_3 | Nightly purge of dead sign-in rows (`auth.purge_dead_auth_rows()`) | The purge job errors in the logs | `SELECT to_regprocedure('auth.purge_dead_auth_rows()');` |
| V143_4 | Takes company-wide document, letter and profile permissions off department managers | Managers can read any employee's documents or CTC (security) | `SELECT count(*)=0 FROM rbac.role_permissions rp JOIN rbac.roles r ON r.id=rp.role_id WHERE r.code='DEPT_MANAGER' AND rp.permission_code='hrms.document.read';` |
| V143_5 | New `attendance.workforce.admin` (shift definitions + manual attendance) for HR / owner / admin | HR can't edit shifts or add manual attendance | `SELECT 1 FROM rbac.permissions WHERE code='attendance.workforce.admin';` |
| V143_6 | Approval delegations (`platform.approver_delegations`) | Profile → Approval delegation errors; approvals may fail | `SELECT to_regclass('platform.approver_delegations');` |
| V143_7 | Document types + verification (`document_mgmt.document_types`, verification columns) | Documents pages and review queue error | `SELECT to_regclass('document_mgmt.document_types');` |
| V143_8 | Removing a checklist task no longer breaks onboardings in progress (FK → `ON DELETE SET NULL`) | That delete still fails with a 500 (no data loss) | `SELECT pg_get_constraintdef(oid) LIKE '%ON DELETE SET NULL%' FROM pg_constraint WHERE conname='onboarding_instance_tasks_task_id_fkey';` |
| V143_9 | ADMIN gets performance read + write; new `hrms.kpi.progress` for DEPT_MANAGER, OWNER, SUPER_ADMIN | ADMIN can't see appraisals and KPIs; **without the OWNER grant the new backend refuses to start** | `SELECT count(*)=3 FROM rbac.role_permissions rp JOIN rbac.roles r ON r.id=rp.role_id WHERE rp.permission_code='hrms.kpi.progress' AND r.tenant_id IS NULL;` |

After the last one, sanity-check the app role:
```sql
SET ROLE ut_app;
SELECT count(*) FROM document_mgmt.document_types;   -- no permission error
RESET ROLE;
```

## 4. Deploy the backend (10–15 min)

1. GitHub → Actions → **Deploy backend to Cloud Run** → **Run workflow** on `main` (or re-run the latest run).
   - The job builds, runs the unit tests (they pass locally: 94 run, 0 failed), builds the image, deploys a revision and smoke-tests `/api/actuator/health`.
2. If Actions isn't set up (repo variables `GCP_*` missing), deploy by hand (RUNBOOK §1b): `cd deployments/gcp && ./provision.sh deploy`.
3. Confirm the new revision is serving, and on the right commit:
   ```bash
   gcloud run revisions list --service unifiedtree-saas --region asia-south1 --limit 3
   curl -s https://<service-url>/api/actuator/health     # {"status":"UP"}
   ```
4. Check the logs of the new revision for these three lines:
   - `OwnerPermissionInvariantCheck: PASS`
   - `KPI at-risk sweep: … marked at risk`
   - `Started HrmsApplication`
   If you see `Application run failed`, read the reason. It's almost always a migration from step 3 that wasn't applied.

**Rollback:** re-point traffic to the previous revision (RUNBOOK §2), which takes about 30 s. The migrations are additive, so the old backend still runs on the new schema. Don't restore the database unless data is actually wrong.

## 5. Frontend (5 min)

- `apps/platform` deploys on Vercel (`apps/platform/vercel.json`). Check that the latest production deployment is on the same `main` commit, and redeploy if not.
- Check that the production build points at the production API: `VITE_API_BASE_URL` / `VITE_API_URL` in the Vercel project env, with `apps/platform/.env.production` as the fallback.

## 6. Production settings to check

| Setting | Why |
|---|---|
| `R2_DOCUMENT_BUCKET` and the R2 credentials | Uploading documents and opening them ("View file") need document storage. Without it, uploads answer "Document storage is not configured" and files can't be opened. |
| Mail provider (`MAIL_PROVIDER=brevo` + key) | Invitations, offer emails, letter sends and reminders. |
| `HRMS_GEOFENCE_ENFORCE` | On by default. Punches outside a zone are blocked. |
| `UNIFIEDTREE_FACE_WORKER_URL` | `provision.sh` has a placeholder (`ut-face-worker-xxxx`). Make sure the real URL is set, or face punches fail. |

## 7. Smoke test in production (20 min)

Use real accounts for each role. **Don't process, lock or pay a real payroll run.** Tick each line:

**Owner / HR**
- [ ] Sign in (checks V143_2); the dashboard loads.
- [ ] Employees list; open one employee; every tab loads.
- [ ] Attendance → Daily Logs; Muster roll (today reads "Not marked yet", not "Absent"); Manual entry saves.
- [ ] Leave → Approvals; approve or reject a test request.
- [ ] Payroll → Dashboard and a past run opens (don't process). Bank page opens.
- [ ] Hiring board; Onboarding & assets (three views); Documents; Docs to review.
- [ ] Performance: Review cycles, Employee reviews, Goals & KPIs.
- [ ] Compliance, Reports Center (download one CSV), Users & access, Roles & permissions, Audit logs.

**Admin** (a user with the ADMIN role)
- [ ] Performance shows cycles, reviews and KPIs (V143_9), and can create a KPI and record progress.

**Department manager**
- [ ] My team page; Performance → Employee reviews shows only their team; KPIs show "Your team's goals & KPIs".
- [ ] Manual entry: the form opens but Save is off, with a note (V143_5).
- [ ] Can't see job offers (V143_1) or other people's documents (V143_4).

**Employee**
- [ ] Sign in on web **and** the mobile app; punch in (face + geofence).
- [ ] My workspace (Overview, Payslips, Salary, Work from home, Shift change); apply for leave.
- [ ] Performance → My reviews, My goals; Learning → enrol in a program.
- [ ] Documents → My documents; Policies → acknowledge one.

If something fails: collect the Cloud Run log line plus the browser's network response, and roll back the revision if it's severe (step 4).
