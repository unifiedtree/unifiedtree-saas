# Leave, Expenses & Advances — page briefs

This group covers the three employee-money-and-time workflows that every role touches: applying for and approving leave (plus leave types and the holiday calendar), filing and reimbursing expense claims (plus reimbursement batches and policies), and requesting, approving, disbursing and recovering salary advances.
Sidebar homes: **Leave Management › Leave Operations Center** (`/hrms/leave`), **Expense Management › Expense Center** (`/hrms/expenses`), **Payroll › Advances & Loans** (`/hrms/advances`). All three routes sit under `ModuleGate moduleKey="hrms"`.
Roles (from `layouts/PlatformShell.tsx`): `R_ADMIN_MGR` = OWNER, SUPER_ADMIN, COMPANY_ADMIN, HR_MANAGER, FINANCE_LEAD, DEPT_MANAGER; `R_ESS` = EMPLOYEE; `R_HR` = OWNER, SUPER_ADMIN, COMPANY_ADMIN, HR_MANAGER. Seeded permission grants are quoted from `backend/app/hrms-app/src/main/resources/db/canonical/V004/V017/V023/V024/V029/V035/V064/V066/V067/V068/V085/V090/V124`. Seeded system roles are SUPER_ADMIN (…0001, every permission via V017 fan-out), HR_MANAGER (…0002), FINANCE_LEAD (…0003), EMPLOYEE (…0004), DEPT_MANAGER (…0005) from V004, plus OWNER (…0010, every non-platform permission via V064) and ADMIN (…0011) from V035. **COMPANY_ADMIN is not a seeded role** — it exists only as a frontend role bucket (`useRoles.ts` `ADMIN_ROLES`, PlatformShell) and as an optional tenant-created role code (V109); V029 and V085 label role …0003 "COMPANY_ADMIN" by mistake (V066 corrects it to FINANCE_LEAD), so grants those comments attribute to COMPANY_ADMIN actually belong to FINANCE_LEAD.

All paths below are relative to `apps/platform/src/`. Money is formatted with `inr()` → `₹1,20,000`; dates with `format(d, 'd MMM yyyy')` → `18 Sep 2026`.

### Purpose
One page for the whole leave loop. An employee comes here to see their leave history, apply for leave, and check balances. A DEPT_MANAGER / HR_MANAGER / admin comes here to approve or reject pending leave and WFH requests, see what they already decided, and (HR/admin only) maintain leave types and the company holiday calendar.

### Data shown
- My Leaves rows — `useMyLeaves(page, pageSize)` → `GET /v1/leave/my?page&size` (`leave.balance.read`): `leaveTypeName, status (PENDING | APPROVED | REJECTED | CANCELLED | PENDING_L2), startDate, endDate, totalDays, reason`. Status labels: Pending / Approved / Rejected / Cancelled / **Awaiting HR** (PENDING_L2, purple).
- Apply form — `useLeaveTypes(companyId)` → `GET /v1/leave/types?companyId` (active types only shown); `useMyBalances(year)` → `GET /v1/leave/my/balances?year`; `useMyLeaves(0)` for the overlap check; `useWeekendDays(companyId)` → `GET /v1/settings/hr-configuration/weekend-days?companyId` (falls back to Sat+Sun); `useCompanies()` + `useCurrentUser()` for `companyId`.
- Balances cards — `useMyBalances(currentYear)`: `leaveTypeName, available, used, totalEntitlement, pending, carryForward`.
- Approvals — `usePendingApprovals(page)` → `GET /v1/leave/approvals/pending?page&size=20` (`hrms.leave.approve.l1`; tenant-wide when the caller also holds `hrms.leave.approve.l2`, else only requests routed to this manager) merged with `usePendingWfhApprovals(page)` → `GET /v1/wfh/pending-approvals?page&size=20` (`wfh.approve`; same L2 broadening). Rows sorted by `createdAt` desc; both queries share one page index and both poll every 30 s (`refetchInterval`).
- History — `useApprovalsHistory(page)` → `GET /v1/leave/approvals/history?page&size=20` (leave only; WFH decisions are not shown).
- Leave Calendar — **no hook; hard-coded markup**. (`useLeaveOverview` → `GET /v1/leave/overview` exists in `api/useLeave.ts` but is only used by the dashboards.)
- Leave Types — `useLeaveTypes(companies[0].id)`: `name, code, category, annualEntitlement, maxConsecutiveDays, isCarryForwardAllowed, maxCarryForwardDays, isPaidLeave, minNoticeDays, applicableGender, description, isActive`.
- Holidays — `useHolidays(companies[0].id, year)` → `GET /v1/settings/holidays?companyId&year`: `holidayDate, holidayName, holidayType, description`.

### Rules & permissions
- Admin bucket (OWNER / SUPER_ADMIN / COMPANY_ADMIN / ADMIN) never sees personal tabs (`Leave.tsx` `roleFilteredTabs`).
- Apply: start date ≥ today (local, not UTC); end ≥ start; half-day = 0.5 day and forces end = start; reason 10–500 chars; requested days (business days excluding tenant weekend days from HR configuration) must not exceed `available` for the chosen type; no overlap with own PENDING / PENDING_L2 / APPROVED requests. Server recomputes days including holidays.
- Cancel only for PENDING or APPROVED requests; backend enforces ownership (`leave.request.self`).
- Approvals scope: L1 holders with `hrms.leave.approve.l2` (SUPER_ADMIN, OWNER, HR_MANAGER — V023/V064) see every pending request in the tenant; a plain DEPT_MANAGER sees only requests routed to them (`LeaveController.pendingApprovals`, `WfhController.pendingApprovals`). History follows the same split.
- WFH rejection must carry a comment (`WFH_REJECT_REASON_REQUIRED`).
- Leave Types and Holidays are readable by everyone; write affordances are gated on `leave.type.write` / `settings.holidays.write`. Both resolve their company as `companies[0]` — a multi-company tenant has no company switcher here.
- Holiday date is clamped to the viewed year (`min`/`max` on the input).

### Purpose
Employees file expense claims (multi-line, category-capped) and watch them move Submitted → Approved → Reimbursed. Managers approve or reject claims routed to them; finance marks approved claims reimbursed (one by one, or by building a reimbursement batch and recording the bank payment). HR/finance maintain per-category policy caps.

### Rules & permissions
- Claim must have a title and at least one line with amount > 0 and a date. Per-category subtotal is checked against the tightest **active** policy cap (mirrors `ExpenseService.enforceCategoryCaps`); server rejects with `EXPENSE_POLICY_CAP_EXCEEDED` (422).
- Multi-company tenants pick a company; single-company tenants send `companyId` undefined and the server uses the employee's company.
- Approvals scope: `hrms.expense.reimbursement` holders see the whole tenant; plain `claim.approve` holders (DEPT_MANAGER) see only claims routed to them (`ExpenseController.pendingApprovals`). Queue includes SUBMITTED and APPROVED.
- Batch lifecycle: build (DRAFT, includes approved claims through the cutoff not already reserved; existing draft for the same company + cutoff is refreshed) → post → mark-paid (needs a payment reference) → or cancel (releases claims). `revert-claims` endpoint exists on the backend but has **no UI**.
- Policy restore sends only `isActive: true` so caps are preserved.

### Rules & permissions
- Request: amount > 0; repayment 1–60 whole months; monthly deduction = amount ÷ months (preview).
- Self-approval / self-disbursement blocked in UI (`isOwn`) and on the server ("Server retains the identity check").
- Scope (Company list, Approvals, decide, detail): `hrms.advance.disburse` holders (FINANCE_LEAD, OWNER, SUPER_ADMIN) see the tenant; `approve`-only holders (DEPT_MANAGER, HR_MANAGER) see and act on only advances routed to them (`AdvanceController.listRequests / pendingApprovals / decide`). Approved advances stay in the queue until disbursed.
- Disbursement is a record, not a transfer; it seeds the payroll recovery schedule; recovery starts next month.
- Foreclose / write-off need `hrms.advance.foreclose` (OWNER, SUPER_ADMIN, HR_MANAGER, FINANCE_LEAD per V090); skip-month needs `approve` and, server-side, the caller must be the routed approver or a `disburse` holder (`AdvanceRecoveryController.skipMonth`); every recovery action requires a reason; deferral moves the installment to the end without changing the total.
